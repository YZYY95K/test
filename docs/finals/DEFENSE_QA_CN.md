# DevFlow 决赛高压答辩题库

回答原则：先给结论，再给可重跑证据，最后主动说明边界。所有数字以最终提交
commit 的证据报告为准；本文中的“当前”指 2026-07-28 的候选工作树和已记录现场
证据，不自动继承到未来版本。

## 场景价值与结果可信度

### 1. 这不就是把软件流水线拆成六个提示词吗？

不是。角色拆分只是表面，核心是执行边界：Leader 独占拆解和状态迁移，Worker 只能
接收自己拥有的 Skill，交接绑定父任务与摘要，Tester 的通过必须有隔离测试完整性
证明，T4/T5 必须暂停给外部人类。可检查
[边界与 MCP 模型](../BOUNDARIES_AND_MCP.md)和对应测试，而不是只看角色描述。

### 2. 为什么这个问题一定要多 Agent，单 Agent 不行吗？

单 Agent 能写出候选补丁，但同一主体同时写、测、审、批准会造成权限与证据自证。
DevFlow 把定位、生成、验证、评审和编排分给不同责任主体，并在运行时阻止越权。
代价是通信与调度开销，因此只保留六个互不重叠角色，而不是追求 Agent 数量。

### 3. 你们如何定义“问题真的解决了”？

不是模型说“完成”，而是固定 revision 上满足联合判据：问题与根因有证据；补丁在
定位范围内；canonical checkout 未被 Worker 修改；基线失败、候选通过且测试未被
削弱；评审与安全门通过；高风险批准有效；终态回执、路由账本与审计链一致。缺一项
都不能进入 `verified`。

### 4. 你们当前真实修复成功率是多少？

目前不能给出真实仓库端到端成功率。三仓库 21 个修复任务已有固定版本和执行清单，
但当前报告是 `attempted=0`、`executed=0`、`success_rate=null`。历史 24 项数据是路由/边界基准，
不是缺陷修复率。完成隔离执行后才报告成功率、成本、P50/P95、安全率和人工介入率。

### 5. 演示里的 calculator 会不会只是为 Demo 写死的？

它是一个确定性验收夹具，不代表真实仓库泛化能力。价值在于它现场运行真实补丁、
真实基线/候选测试、评审、经验沉淀和持久账本，方便任何评委离线复跑。泛化能力要由
固定开源仓库基准另行证明，二者不混为一谈。

### 6. 你们怎样避免“测试绿了但业务没修好”？

Tester 同时比较基线和候选，不接受只有“退出码 0”的结果；完整性 attestation 绑定
测试清单、命令、策略和候选摘要，并拒绝删除测试、引入 skip/xfail 或篡改收集逻辑。
Reviewer 再检查正确性、安全和范围。但任何有限测试都不能证明无缺陷，因此输出是
“在声明的验证范围内通过”，不是数学上的完全正确。

## 多 Agent 身份、协作与失败恢复

### 7. Agent 怎么知道自己是谁？靠 system prompt 吗？

不只靠提示词。身份同时存在于 AgentTeams 角色/Pod、角色专属包、Skill 所有权、
TeamHarness 进程角色和 MCP Consumer。请求中的 `role=leader` 不能改变进程身份；
真实环境已观察 Worker 冒充 Leader 被 `forbidden_tool` 拒绝。提示词负责行为引导，
运行时身份负责授权。

### 8. 为什么是六个 Agent？能否再合并？

六个角色对应六种互相制衡的责任：编排、分类、定位、生成、测试、评审/沉淀。
Triage 不读代码，Locator 不写代码，Coder 不跑测试，Tester 不改代码，Reviewer 不
合并，Leader 不替代任何领域工作。再合并会恢复自证或扩大权限；再拆分则暂未带来
足以抵消通信成本的独立责任。

### 9. Leader 会不会成为单点故障或“超级 Agent”？

它是调度权威，因此确实是控制面单点，但不是能力超级集合。Leader 不能生成补丁、
测试、评审、合并或代替人批准；状态由持久账本、幂等键、租约和审计链支持恢复。
生产高可用仍需外部选主和故障演练，当前实现不能宣称完成分布式共识。

### 10. Agent 间通信如何减少损耗？

使用中心辐射而非全连接：Worker 只回 Leader；传递类型化最小制品，而不是完整聊天
历史；大对象使用摘要与共享制品引用；父路由摘要阻止上下文串线；`ready/retry/blocked`
与传输状态有精确语义。减少 token 只是副作用，主要收益是歧义可被验证器拒绝。

### 11. 为什么不让 Tester 直接通知 Coder，速度不是更快吗？

直接边会绕过全局预算、候选摘要校验、脱敏和审计权威。Tester 只把失败交给 Leader；
Leader 验证完整结果后生成有界 `TestFailureEvidence` 再路由 Coder。多一次跳转换来一致
状态和明确责任，且避免原始日志携带敏感信息横向传播。

### 12. 两个 Worker 给出冲突结论时谁说了算？

Leader 只按证据门仲裁，不按语言置信度投票。红测不能被 Reviewer 的“看起来正确”
覆盖，高/严重安全发现不能被绿测覆盖，缺失 attestation 不能被成功状态覆盖。需要
新需求判断时升级给人，而不是让模型互相辩论到超时。

### 13. 失败会不会无限循环烧钱？

不会。每个 canonical Coder 路由只授权一次模型调用，验证失败与测试失败共享一个
issue-global 的 1..3 生成预算；同一路由重复交付复用结果，冲突会审计并拒绝。第三次
仍失败就升级，不生成第四个候选。

### 14. 你们宣称 exactly-once 吗？

不作绝对宣称。本地持久账本为路由提供跨进程 claim、租约恢复和结果封存，可证明
DevFlow 调度层对 canonical route 的一次有效执行语义；外部 GitHub、CI 或部署系统
可能在超时前已发生副作用，必须依赖提供方幂等键和 readback。我们明确写成
“受边界约束的一次有效路由”，不是全世界 exactly-once。

### 15. Agent 崩溃后任务怎么办？

未封存路由由有期限租约保护；过期租约可被恢复，已封存结果按幂等键读回，冲突结果
不会覆盖原结果。审计链记录 claim、seal 和恢复。集群级 Pod/控制面故障恢复仍需用
最终部署演练证明，不能由本地 SQLite 测试外推。

## Skill、MCP、RAG 与安全

### 16. 你们的 Skill 与普通 prompt 有什么区别？

每个 Skill 是版本化可发布资产，包含触发条件、输入/输出契约、正反例、验证器、
所有者、失败语义、安全边界和升级/回滚策略；角色包按 Skill 最小分发，AgentTeams
提交和 Leader 验收前都会执行验证器。Prompt 是其中一部分，不是完整 Skill。

### 17. 七个 Skill 都拿到 100 分，是否等于效果完美？

不等于。7/7 的 100/100 是静态工程质量门，只证明文档和结构满足内部 rubric；14 个
行为案例当前也只是结构门。实际效果必须看固定模型的成对行为评估和真实仓库重放，
这些结果要对最终版本重新冻结。

### 18. Skill 如何防止角色边界漂移？

契约声明唯一 owner；构建时比较配置、契约与角色包；运行时 guard 在 ACK、提交和
验收前校验当前角色、Skill、artifact 和固定 validator/contract 摘要。真实集群曾因
持久工作区恢复旧 authorizer 而返回 `SKILL_RUNTIME_VERSION_MISMATCH`，说明漂移会
失败暴露，而不是静默继续。

### 19. MCP 接得多就更好吗？

不是，官方也不按接入数量直接计分。DevFlow 只在能力需要外部副作用或证据时使用
MCP，并要求 Agent∩Skill∩server∩tool∩参数范围同时命中；未声明组合默认拒绝。
Locator 只有范围绑定的 GitHub 读取，Tester 只有隔离 CI，当前 Reviewer 没有 GitHub
写权限。

### 20. 怎样证明 MCP 边界不是配置文件里的“伪实现”？

真实集群已做固定仓库/revision/path 的正向 GitHub 读取，并分别观察同 capability
错路径 403、Reviewer 身份 403、Locator 直连 Broker 被 NetworkPolicy 阻断；receipt
摘要可重算。它证明的是这一个精确读取边界，不证明任意仓库或完整六阶段。

### 21. Agent 能不能自己伪造身份或审批字段？

不能靠请求字段提权。TeamHarness 从进程身份、根拥有账本和持久项目状态派生权威
事实，并替换或拒绝调用者自报的角色/风险。审批必须由外部私钥对精确目标签名；
Agent 产生的 JSON、Matrix 文本或“用户已同意”都不是授权。

### 22. T4/T5 人工审批到底绑定什么？

绑定 approval domain、策略公钥摘要、项目与 incarnation、risk tier、revision、
候选、测试证据、评审结论、nonce 和有效期。Leader 验证后一次性消费；换项目、改
任何摘要、过期或重放都拒绝。Human Authority 只授权该目标，不获得环境的通用权限。

### 23. 真实集群已经完成 T4 人工恢复了吗？

没有。真实环境目前证明 T4 项目进入 `paused`，无批准恢复被稳定拒绝；签名后恢复和
重放拒绝已有本地集成测试，但真人外部签名的集群成功录像仍是发布阻断项。我们不会
用“拒绝成功”替代“批准闭环”。

### 24. RAG 如何避免跨租户或旧代码污染？

查询必须精确绑定 tenant、repository 和不可变 revision；记录内容、metadata 和
向量由服务端 HMAC 鉴别。缺密钥、分支名式 revision、过期记录、跨租户结果或任一
内容被修改都 fail closed。离线 `local-hash` 只用于确定性降级，不宣称等同生产语义
检索质量。

### 25. 经验库会不会把一次错误修复沉淀成长期污染？

Experience Distiller 只接受 Leader 路由的 `VerifiedRunBundle`，其中测试、评审、
批准和终态 receipt 摘要必须一致。失败、拒绝、待人工、被篡改或含密钥的内容在写入
前被拒绝。其边界是防止未验证经验进入可信库，不是保证所有已通过经验永远正确。

### 26. 密钥怎么保护？

Worker 不接收原始提供方密钥，而接收短期、范围绑定的能力句柄；真实凭据保留在可信
Broker/适配器。日志和公开证据只保留摘要，secret-shaped 输出会被阻断。已有凭据若
曾在聊天或终端暴露必须轮换，不能因为仓库未提交就视为安全。

### 27. 你们有强 OS 沙箱吗？

当前 OpenClaw AgentTeams 布局没有，审计明确为
`strongBoundaryEnforceable=false`。原因包括 UID 0、策略/凭据与可写工作区共置、
通用执行面等。现有保证是逻辑角色、进程 guard、MCP/网络和应用层边界；强敌对 root
隔离需非 root、只读外置策略、侧车凭据代理和不可变操作面后再验收。

### 28. 审计链能防管理员改数据库吗？

哈希链能检测条目被改、删或重排，并把终态绑定到链头；若攻击者同时控制数据库和
所有签名/锚点，则本地链不能独立证明历史。生产版应把链头周期性锚定到外部只写存储
或透明日志。当前表述是“可检测篡改”，不是“不可篡改”。

## 工程落地、测评与决赛证据

### 29. CI/CD、OTLP、Prometheus 是真的还是 YAML 占位？

仓库已有隔离测试服务、CI/CD 工具、批量 OTLP/gRPC 导出、loopback-only Prometheus
端点、审计和回滚策略，并有本地测试。决赛级陈述还需要在干净服务器保留真实 MCP
receipt、collector trace、Prometheus scrape 和回滚故障注入；配置存在不能代替现场
集成证据。

### 30. 当前 AgentTeams 到底真实跑到了什么程度？

真实环境已运行 1 Leader+5 Worker、机器人自动交接、一个两节点 T2 生命周期、一次
operator-driven T2 GitHub 边界成功、Worker 越权拒绝、固定七 Skill 策略收敛、
T4 暂停与无批准拒绝。尚未证明同一项目六阶段、Tester→Coder 现场重试或真人 T4
签名恢复。完整细节见[现场证据](../evidence/AGENTTEAMS_LIVE_20260727.md)。

### 31. 本地测试通过多少？覆盖率多少？

2026-07-29 最近一次决赛 RC 全量门为 1,033 passed、17 skipped、84.79%（6,324
statements / 962 missed）。该数字是 provenance 所指构建 commit 的本地工程证据，
不能表述为官方评分、集群完整闭环或模型仓库基准成绩。
答辩时只读取绑定最终 commit 的新报告并说明跳过项原因；不能用聚焦测试数、收集
数或旧报告替代最终全量结果。

### 32. 网络断了还能演示吗？

可以展示本地可复现证据：凭据无关 Demo 会现场生成新的 JSON、SQLite 路由账本和
哈希链；失败恢复与 T4 精确审批有聚焦集成测试。若本机也失败，则播放绑定最终 commit
和 SHA-256 的录屏，并明确标记 `RECORDED REHEARSAL`，绝不伪装成在线集群。

### 33. 成本和时延怎么评估？

在 21 个固定任务真实执行时，以任务为单位记录模型/嵌入/工具调用、输入输出 token、
墙钟时间、P50/P95、重试次数和人工等待时间；失败也进入分母。当前尚未执行，因此
不会用理想估算或单次 Demo 外推成本。

### 34. 系统如何扩展到更多仓库和团队？

复用单元是契约、Skill 和最小 MCP grant，不是复制一整套聊天记录。新仓库需要新增
版本固定、测试命令、路径策略与 RAG scope；新角色只有出现独立责任和权限时才加入。
控制面水平扩展仍需验证共享账本、选主和外部副作用幂等，当前不宣称无限扩展。

### 35. 你们如何对应官方五项评分？

场景价值用固定仓库任务和可量化结果；多 Agent 用 AgentTeams 真实状态与失败/审批
闭环；Skill 用七个版本化资产及验证器；工程安全用隔离 CI、MCP、RAG、观测和审计；
开源用 Apache-2.0、可部署仓库、SBOM 与复现实验。权重和放行条件见
[决赛验收矩阵](ACCEPTANCE_MATRIX_CN.md)，不会用组件数量冒充得分。

### 36. 为什么你们值得夺冠？

我们不声称奖项结果。可竞争之处是把多 Agent 最难的身份、边界、通信、失败和人工
授权做成可执行契约，并主动区分本地、真实集群与待完成证据。最终是否达到冠军水平，
应由固定任务结果、现场闭环、可复现工程与评委评分共同决定。
